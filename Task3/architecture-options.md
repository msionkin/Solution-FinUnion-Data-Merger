# Сравнение архитектурных вариантов

## Варианты

| Подход | Плюсы | Минусы | Когда подходит | Применимость к FinUnion + RetailBank |
|---|---|---|---|---|
| **DWH на PostgreSQL** | Строгая схема (schema-on-write), ACID, SQL. Проще сверять данные с учётом. FU DWH уже работает на PostgreSQL, есть команда. Быстрый запуск | Вертикальное масштабирование; тяжёлые запросы по многолетней детальной истории медленные. Дорого хранить события и сырые данные. Не подходит для полуструктурированных данных и ML | Стабильная модель показателей, регламентная отчётность, умеренный объём (миллионы — сотни миллионов строк) | **Высокая** для отчётности: промежуточная управленческая отчётность через 3 месяца и регуляторная отчётность в целевом состоянии. Не подходит для полной истории карточных операций и архивов RB |
| **Data Lakehouse** (Iceberg + Trino на S3) | Дешёвое масштабируемое хранение, открытые форматы. ACID и снимки таблиц (time travel). Хранение и вычисления разделены. Работает с событиями, JSON, файлами, ML | Сложнее эксплуатация: нужно управлять метаданными, версиями таблиц, ACID-транзакциями поверх объектного хранилища. Без governance превращается в «болото данных». | Большая история, события, полуструктурированные данные, разнородные данные (логи, события, файлы, таблицы), нужны аналитика, ML/Data Science | **Высокая** для истории и событий: полная история операций, карточные события, CDC-история, архив RB после вывода систем, данные для скоринга и антифрода |
| **Data Mesh** | Доменное владение: данные ведёт команда, которая знает их смысл. Data-продукты с контрактами, центральная команда не становится узким местом | Нужны зрелые доменные команды и платформа самообслуживания. Высокие организационные затраты. Без федеративного управления идентификаторы и метрики расходятся | Много доменов и команд, центральная команда данных стала узким местом | **Частичная.** Полный Data Mesh за 12 месяцев нереалистичен: идёт слияние, UCID и справочники ещё формируются. Полезны элементы: доменное владение, data-продукты, контракты, федеративные правила |

## Выбранный подход: гибридная архитектура

**DWH на PostgreSQL + Data Lakehouse + элементы Data Mesh на общей платформе.**

- **Через 3 месяца:** FU DWH на PostgreSQL — единая управленческая отчётность. Данные RB поступают через CDC и Kafka, преобразуются внутри DWH с помощью dbt (ELT). Lakehouse ещё не нужен — решаем минимальную задачу быстро.
- **Через 12 месяцев:** все данные попадают в Lakehouse (Bronze → Silver → Gold). В нём хранится детальная история и события, из него собираются data-продукты. DWH на PostgreSQL загружается из Silver и остаётся местом регламентированной отчётности. Из Data Mesh берём доменных владельцев и data-продукты ([data-products.md](data-products.md)), а платформа, безопасность и стандарты остаются общими.

**Обоснование:**
1. Каждая нагрузка — на подходящем хранилище. Отчётности нужны строгая модель и сверка с учётом (DWH), истории и событиям — дешёвое масштабируемое хранение (Lakehouse).
2. PostgreSQL остаётся на посильном объёме: детальные операции только за 2 года, тяжёлые вычисления — в Spark. Так не нужен переход на MPP (это можно будет рассмотреть в будущем), а экспертиза и модели промежуточного DWH сохраняются.
3. Системы RB можно вывести, не теряя истории: она переносится в Lakehouse.
4. Элементы Data Mesh закрепляют владение данными за бизнес-доменами (см. [Task2/data-ownership.md](../Task2/data-ownership.md)), а общие UCID, справочники MDM и DataHub не дают доменам разойтись.
