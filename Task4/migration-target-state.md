# Образ целевого результата (12 месяцев)

Целевая архитектура — [Task3/target-data-architecture.md](../Task3/target-data-architecture.md), мастер-системы — [Task2/master-systems.md](../Task2/master-systems.md). Номера потоков F — из [Task2/data-flows.md](../Task2/data-flows.md), пайплайнов P — из [Task3/data-pipelines.md](../Task3/data-pipelines.md).

| Вопрос | Что меняется за 12 месяцев |
|---|---|
| **Какие системы остаются** | **Операционные:** FU CRM (для клиента — реплика MDM), FU Core Banking, FU Card Processing, FU Loan System, Consent Management (новая система).<br>**Мастер-данные:** MDM (Customer Hub + Reference Data) в режиме centralized.<br>**Интеграция:** FU ESB (только синхронные вызовы), Kafka + Debezium CDC + Schema Registry, Airflow (первичная загрузка и сверка coexistence).<br>**Аналитика:** Data Lakehouse (S3 на Ceph + Apache Iceberg, Iceberg REST Catalog, Spark, Trino), DWH на PostgreSQL (бывший FU DWH, загружается из Silver), FU BI с семантическим слоем, Airflow, dbt + Great Expectations, DataHub, Vault, объектное хранилище (WORM) |
| **Какие выводятся из эксплуатации** | RB CRM, RB Core, RB Cards, RB Loans, RB DWH, RB BI, point-to-point интеграции RB, FU Data Lake.<br>Временные компоненты перехода: CDC-коннекторы к базам RB, поток RB → FU CRM (F09), промежуточная загрузка DWH через Kafka Connect JDBC Sink (P1), batch ETL из реплик FU в DWH (F10), потоки coexistence CRM → MDM (F01, F02) |
| **Какие данные мигрируются** | **В операционные системы FU** (когортами клиентов): открытые договоры и участие в них, счета с остатками, вклады, кредиты с графиками и просрочкой, карты, незавершённые платежи, открытые обращения.<br>**В MDM:** клиенты RB, справочники RB с маппингом на FU.<br>**В Consent Management:** согласия FU CRM и RB CRM с историей выдачи и отзыва.<br>**В Lakehouse:** история RB (RB DWH, Core, Cards, Loans, CRM) в `archive_rb` + исходные выгрузки в WORM; история FU Data Lake; CDC-история всех систем FU |
| **Какие потоки переключаются** | **Клиент** (10-й месяц, cutover). Было: клиента заводят и меняют в FU CRM и RB CRM, изменения по CDC уходят в MDM (F01, F02), MDM возвращает в CRM золотую запись (F05). Стало: клиента создают и меняют только через API MDM (P3), ESB направляет туда запросы из CRM и каналов, FU CRM получает изменения как реплика.<br>**Согласия** (4–6-й месяц). Было: согласия выдаются и отзываются в FU CRM и RB CRM и по CDC расходятся в MDM, CRM другого банка и DWH (F08). Стало: согласия выдаются и отзываются только в Consent Management, он становится источником потока F08 для остальных систем (отзыв доходит ≤ 15 мин); в Lakehouse согласия попадают по CDC из Consent Management (P4).<br>**Загрузка аналитики** (6–8-й месяц). Было: DWH загружается напрямую из операционных систем: FU — batch ETL с реплик (F10), RB — через CDC (F11, P1). Стало: все CDC-потоки идут в Lakehouse (Bronze, затем Silver, P4), DWH загружается только из Silver (P5).<br>**Регуляторная отчётность RB** (4–6-й месяц). Было: строится в RB DWH (F16). Стало: строится в DWH отдельно по юрлицу RB, после присоединения (9-й месяц) — единая отчётность объединённого банка из DWH.<br>**BI** (6–8-й месяц). Было: пользователи RB работают в RB BI. Стало: все пользователи работают в FU BI.<br>**Доступ к истории FU Data Lake** (4–6-й месяц). Было: потребители читают данные напрямую из FU Data Lake. Стало: история перенесена в Lakehouse, потребители читают её через Trino.<br>**Операционные вызовы CRM** (6–9-й месяц, по волнам). Было: CRM вызывает системы RB по P2P, системы FU — через ESB (F18). Стало: после переноса когорты все вызовы идут через ESB в системы FU, P2P-интеграции RB не используются |
| **Какие критерии подтверждают завершение** | 1) 100% клиентов и портфелей RB в системах FU; остатки, задолженность и число договоров сверены по каждой волне без расхождений.<br>2) Регуляторная отчётность объединённого банка за закрытый период сдана из DWH без исправлений.<br>3) Системы RB и FU Data Lake 30 дней не получают новых транзакций, запросов и подключений (по журналам БД и BI), затем выведены; архив `archive_rb` сверен с отчётностью RB.<br>4) Клиент создаётся и меняется только через API MDM, доля дублей < 0,5%, прямых изменений клиента в CRM нет.<br>5) Data-продукты опубликованы с владельцем, контрактом и SLA.<br>6) Все наборы данных зарегистрированы в DataHub с владельцем и lineage.<br>7) Временные компоненты перехода отключены.<br>8) Владельцы данных подписали приёмку |
