# Cutover-план: клиентские данные

**Что переключаем.** MDM Customer Hub переходит из режима coexistence в centralized. Раньше клиента заводили в CRM, изменения через CDC попадали в MDM (F01, F02), и MDM возвращал золотую запись (F05). После переключения клиента создают и меняют только через API MDM (P3), а FU CRM становится репликой.

**Когда.** 10-й месяц, после всех волн переноса: клиенты RB уже в FU CRM, RB CRM работает только для чтения. Окно — ночь с субботы на воскресенье. Окно начинается в момент Tcut: фиксируется offset потока F01, до которого делается финальная выгрузка. Платежи, карты и остатки окно не затрагивает, ограничено только создание и изменение профиля клиента.

**Кто решает Go/No-Go.** Data Owner Клиента — директор по розничному бизнесу (ФЛ) и директор по МСБ (ЮЛ, ИП). Их заместители назначаются заранее. Технический руководитель cutover отвечает за шаги, стюарды Data Office — за разбор данных.

## Шаги

| Шаг | Что делаем |
|---|---|
| **1. Подготовка** (D-14 … D-1) | API MDM (поиск, создание, изменение клиента) прошёл нагрузочный тест на трёхкратном пике: p95 ≤ 1 с. FU CRM и каналы (ДБО, офис) обращаются к API через ESB, новый маршрут пока выключен. Очередь спорных совпадений у стюардов пуста. Два пробных переключения на тестовом стенде с копией production-данных. Резервные копии БД MDM и FU CRM, сохранены offset'ы Kafka потоков F01 и F02. Контакт-центр и офисы предупреждены |
| **2. Data freeze** | **С D-7:** запрещены изменения правил сопоставления и слияния MDM, схем клиентских топиков в Schema Registry, модели данных MDM, массовые обновления клиентов. **В окне от Tcut до переключения (шаги 3–5):** создание и изменение клиентов в FU CRM и каналах не выполняются сразу — заявки принимаются и ставятся в очередь Kafka, обрабатываются после переключения. Стюарды не сливают записи вручную. Операции по счетам и картам идут без ограничений |
| **3. Финальная выгрузка** | На момент Tcut забираем всё, что ещё не обработано MDM: дельту CDC FU CRM (F01) до зафиксированного offset, сообщения из DLQ клиентских топиков, неподтверждённые обновления F05, спорные совпадения. У выгрузки есть ID, диапазон offset и контрольные показатели: количество изменений по типам (создание, изменение, слияние) |
| **4. Загрузка** | Дельта загружается в staging MDM: проверка схемы и форматов (ДУЛ, ИНН, СНИЛС, телефон), сопоставление и слияние, обновление золотых записей. Ошибочные записи не отбрасываются, а уходят в карантин с причиной и ответственным стюардом. Изменения публикуются в FU CRM (F05) и в Core, Cards, Loans (F06), системы подтверждают их применение |
| **5. Сверка** | Проверки из таблицы ниже. По их результатам Data Owner принимает решение Go/No-Go |
| **6. Переключение** | В ESB запросы на создание, изменение и поиск клиента из FU CRM и каналов направляются в API MDM. Потребители не меняют точку входа, меняется только маршрут внутри ESB (Strangler Fig). В БД FU CRM право записи в клиентские таблицы остаётся только у потребителя F05. Поток F01 ставится на паузу, коннектор не удаляется. Обрабатываются заявки из очереди окна. Сотрудник банка создаёт и меняет контрольного клиента через ДБО и CRM, проверяет, что UCID появился в Core, Cards, Loans (≤ 15 мин) |
| **7. Фолбэк** | **Когда:** не выполнена проверка с действием «Остановить», или после переключения ошибки API > 1%, либо p95 > 2 с дольше 15 минут, либо обнаружена потеря изменений. **Как:** ESB возвращает маршрут на CRM (coexistence), права записи в CRM восстанавливаются, поток F01 продолжается с сохранённого offset. Если откат случился до переключения, заявки из очереди окна обрабатывает CRM. Клиенты, созданные через API после переключения, уже есть в FU CRM благодаря F05, поэтому данные не теряются. MDM не применяет события F01, если версия записи в MDM новее, поэтому повтор потока не перезапишет изменения, сделанные через API. После отката — повторная сверка. **Точка необратимости:** D+14 — удаляются коннекторы F01 и F02 и код редактирования клиента в CRM, после чего разрешается вывод RB CRM. После неё ошибки исправляются только в MDM, без отката |
| **8. Мониторинг** | 14 дней стабилизации по метрикам ниже. Стабилизация закончена, если все метрики в норме и контакт-центр не получает жалоб на данные профиля сверх обычного уровня |

## Сверка перед Go/No-Go

| Проверка | Порог | Ответственный | Действие при отклонении |
|---|---|---|---|
| Lag потоков F01 на Tcut, сообщения в DLQ | 0 | Data Engineer | Остановить переключение, догрузить дельту |
| Изменения выгрузки применены в MDM (по ID выгрузки и числу изменений) | 100%, остальное — в карантине с причиной | Data Engineer | Остановить переключение |
| Активные клиенты FU CRM без UCID | 0 | Data Steward | Изолировать записи, разобрать до Go |
| Число активных золотых записей = числу активных клиентов FU CRM в разрезе типа лица, региона и банка происхождения (FU/RB) | 100% совпадение | Data Steward | Изолировать расхождения, разобрать до Go |
| У каждого клиента с действующим счётом, картой или кредитом в Core, Cards, Loans проставлен UCID, и по нему в MDM находится активная золотая запись | 100% | Data Owner | No-Go |
| Доля дублей клиентов | < 0,5% | Data Owner | Решение Go/No-Go |
| Согласия клиентов в Consent Management привязаны к UCID | 100% | Ответственный за обработку ПДн | No-Go |
| Контрольное создание и изменение клиента через API | Успешно, p95 ≤ 1 с | Команда эксплуатации | Фолбэк |

## Мониторинг после переключения

| Метрика | Норма |
|---|---|
| API MDM: время ответа p95, доля ошибок, доступность | ≤ 1 с; < 0,5%; 99,9% |
| Новые клиенты в Core, Cards, Loans без UCID | 0 |
| Доля дублей и новые дубли за сутки | < 0,5%; не выше уровня до cutover |
| Попытки прямой записи в клиентские таблицы FU CRM (аудит БД) | 0 |
| Запросы к RB CRM (кроме архивных) | 0 |
| Полнота ФИО, ДР, ДУЛ | ≥ 99% |
