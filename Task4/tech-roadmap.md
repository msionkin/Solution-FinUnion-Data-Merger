# Технологическая дорожная карта

План миграции ([migration-plan.md](migration-plan.md)) показывает, какого состояния данных достигаем. Дорожная карта показывает, какие платформенные возможности для этого нужны и когда. 
## Дорожная карта по горизонтам

| Горизонт | Этапы плана | Возможности | Зачем нужны |
|---|---|---|---|
| 0–3 месяца | 0. Data discovery (М1)<br>1. Промежуточный контур (М1–3) | MDM (Customer Hub + Reference Data, режим coexistence), Kafka + Debezium CDC + Schema Registry, DWH на PostgreSQL (FU DWH), Airflow, dbt + dbt tests, DataHub | Присвоить клиентам единый UCID и ввести единые справочники; получать данные RB без нагрузки на OLTP; выпустить единую управленческую отчётность; зафиксировать lineage и владельцев данных |
| 3–6 месяцев | 2. Согласия и регуляторная отчётность RB (М4–6)<br>3. Пилот Lakehouse (М4–6)<br>4. Подготовка переноса портфелей (М5–6) | Consent Management; S3 на Ceph, Apache Iceberg + Iceberg REST Catalog, Spark, Trino, Kafka Connect Iceberg Sink (пилот); Vault для псевдонимизации; Great Expectations; инструменты переноса портфелей (срез + дельта CDC, реестр соответствий ID, карантин) | Собрать согласия в едином мастере до переноса клиентов RB; запустить пилот Lakehouse на истории карточных операций и данных FU Data Lake; защитить ПДн в аналитике; отработать перенос портфелей на пробных прогонах |
| 6–9 месяцев | 5. Волны переноса портфелей RB (М6–9)<br>6. Lakehouse в эксплуатации, DWH из Silver (М6–8) | Lakehouse в промышленной эксплуатации, загрузка DWH из Silver; data-продукты с контрактами; семантический слой FU BI | Перенести когорты клиентов RB без остановки сервисов инструментами, отработанными на этапе 4; сделать Lakehouse единой точкой входа данных в аналитику; передать ответственность за данные доменам |
| 9–12 месяцев | 7. Cutover клиентских данных (М10)<br>8. Вывод legacy (М10–12) | MDM в режиме centralized (API MDM через ESB); архив `archive_rb` + WORM-бакеты | Перевести ведение клиента только в MDM; вывести системы RB и FU Data Lake из эксплуатации без потери истории |

## Технологический радар

| Зона | Технологии и подходы | Обоснование |
|---|---|---|
| **Adopt** | PostgreSQL (DWH); MDM (Customer Hub + Reference Data); Kafka + Debezium CDC + Schema Registry (Avro); FU ESB для синхронных вызовов; Airflow; dbt + dbt tests; DataHub; Vault. Подходы: CDC вместо выгрузок из OLTP; миграция когортами с параллельным прогоном и сверкой; матрица мастер-систем и владельцев | Работают в промышленной эксплуатации уже с конца 3-го месяца, когда собран промежуточный контур (этап 1). На них сразу держатся критичные потоки: сопоставление клиентов FU и RB в MDM и единая управленческая отчётность. У команды есть опыт, процессы эксплуатации налажены. Работу FU DWH на PostgreSQL команда знает |
| **Trial** (с переходом в Adopt после этапа плана) | S3 на Ceph, Apache Iceberg + Iceberg REST Catalog, Spark, Trino, Kafka Connect Iceberg Sink; Great Expectations; Consent Management; data-продукты с контрактами (элементы Data Mesh); облачная ML-песочница на анонимизированных данных | Технологии новые для команды. Сначала проверяем на ограниченном сценарии (история карт, согласия, 4 data-продукта), чтобы при ошибке было понятно, в чём она: в новой технологии или в логике миграции. В Adopt технология переходит после успешного завершения своего этапа [плана миграции](migration-plan.md):<br>• стек Lakehouse и Great Expectations — этап 3: FU Data Lake только для чтения, потребители работают через Trino;<br>• Consent Management — этап 2: отзыв согласия доходит до всех систем ≤ 15 мин;<br>• data-продукты — этап 6: у каждого есть владелец, контракт и SLA, все зарегистрированы в DataHub;<br>• облачная ML-песочница — вне этапов плана: когда команда освоит работу в ней и модели на анонимизированных данных начнут давать измеримый результат. |
| **Assess** | MPP-СУБД для DWH; колоночная СУБД для интерактивного BI по большим объёмам; графовая БД (группы связанных заёмщиков, цепочки переводов для антифрода); поисковый движок для контакт-центра; полный Data Mesh с платформой самообслуживания | Сейчас не нужны или не укладываются в 12 месяцев. MPP нужен, если объём DWH превысит возможности PostgreSQL. Графовая БД — когда появятся задачи многоуровневого анализа связей. Полный Data Mesh — когда доменные команды станут зрелыми |
| **Hold** | Новые point-to-point интеграции; прямые запросы BI и аналитики к OLTP и batch ETL из реплик OLTP; развитие RB DWH, RB BI и FU Data Lake; новые асинхронные потоки через ESB; двусторонняя синхронизация мастер-данных по правилу «последнее изменение побеждает»; ПДн и банковская тайна в публичном облаке | Эти подходы увеличивают связанность, нагрузку на операционные системы и стоимость будущей миграции, создают конфликты мастер-систем и нарушают требования ИБ |
