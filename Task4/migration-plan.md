# Инкрементальный план миграции

Диаграмма: [diagrams/migration-roadmap.mmd](diagrams/migration-roadmap.mmd) ([PNG](diagrams/migration-roadmap.png)).

Каждый этап заканчивается проверяемым состоянием, в котором ландшафт непротиворечив и работает. Сроки — ориентир: переход к следующему этапу решают результаты сверки и подтверждение владельца данных (Go/No-Go), а не дата. Этапы частично идут параллельно, порядок задают зависимости.

## Этапы

| Этап | Месяцы | Содержание | Результат (критерий завершения) |
|---|---|---|---|
| **0. Data discovery** | 1 | Инвентаризация систем, таблиц, потоков, владельцев и потребителей FU и RB. Скрытых потребителей RB DWH, RB BI и FU Data Lake ищем по журналам SQL-запросов, подключениям, BI-моделям и заданиям планировщиков. Профилирование качества критичных сущностей | Реестр данных и зависимостей в DataHub. Список потребителей каждой выводимой системы с владельцем |
| **1. Промежуточный контур** | 1–3 | MDM в режиме coexistence: сопоставление клиентов, UCID, маппинг справочников RB → FU. Kafka + Debezium CDC + Schema Registry. Данные RB в FU DWH (P1), разовая загрузка истории RB DWH (F13). Витрины BI, проверки качества, DataHub | Единая управленческая отчётность FU + RB в FU BI. Доля дублей клиентов < 0,5%, клиентов АБС без UCID < 1% |
| **2. Согласия и регуляторная отчётность RB** | 4–6 | Внедрение Consent Management, перенос согласий обоих CRM с историей, поток F08 → Consent Management. Формы отчётности юрлица RB строятся в DWH (данные RB уже поступают через CDC). Параллельный прогон с RB DWH за 2 отчётных периода | Отзыв согласия доходит до всех систем ≤ 15 мин. Отчётность RB сдаётся из DWH, итоги совпадают с RB DWH. RB DWH — только для чтения |
| **3. Пилот Lakehouse (Trial)** | 4–6 | Развёртывание пилотного Lakehouse (S3 на Ceph, Iceberg + Iceberg REST Catalog, Spark, Trino). Загрузка истории карточных операций (S1) из Kafka с псевдонимизацией персональных данных и её обработка по слоям Bronze → Silver → Gold. Перенос истории FU Data Lake в Lakehouse, переключение потребителей FU Data Lake на Trino | FU Data Lake только для чтения, потребители работают через Trino |
| **4. Подготовка переноса портфелей** | 5–6 | Сопоставление всех продуктов, тарифов и подразделений RB с FU в MDM. Настройка в FU Core, Cards, Loans отдельного баланса RB, чтобы до юридического присоединения перенесённые договоры учитывались на балансе RB. Разработка инструментов переноса: срез на T0 и дельта через CDC, повторяемая загрузка (MERGE по ключу), карантин ошибочных записей, реестр соответствий ID RB → FU. Два пробных переноса полного портфеля | В пробном прогоне остатки, задолженность и количество договоров совпадают без необъяснённых расхождений. Go от владельцев данных |
| **5. Волны переноса портфелей RB** | 6–9 | Перенос клиентов вместе с продуктами из RB CRM, Core, Cards, Loans в FU CRM, Core, Cards, Loans тремя волнами: W1 — пилот на сотрудниках RB и ФЛ одного региона, W2 — ФЛ остальных регионов, W3 — МСБ (ЮЛ и ИП). Юридическое присоединение RB (9-й месяц): остатки переводятся с баланса RB на баланс FU | Все клиенты и портфели RB обслуживаются в системах FU. Системы RB только для чтения, CDC-коннекторы RB и поток F09 отключены. Регуляторная отчётность объединённого банка — из DWH |
| **6. Lakehouse в эксплуатации, DWH из Silver** | 6–8 | Все CDC-потоки идут в Bronze (P4), включая CDC систем RB до окончания волн. Параллельный прогон загрузки DWH из Silver (P5) и промежуточной загрузки (P1, F10) за одно закрытие месяца. Сборка в Gold data-продуктов, описание их контрактов и SLA, регистрация в DataHub и подключение потребителей. Перевод пользователей RB BI на FU BI | DWH загружается только из Silver, P1 и F10 отключены. Data-продукты с владельцем, контрактом и SLA зарегистрированы в DataHub. RB BI выведен |
| **7. Cutover клиентских данных** | 10 | Перевод MDM из coexistence в centralized ([cutover-plan.md](cutover-plan.md)) | Клиент создаётся и меняется только через API MDM. FU CRM — реплика, потоки F01 и F02 отключены |
| **8. Вывод legacy** | 10–12 | Архивирование RB DWH, Core, Cards, Loans, CRM в `archive_rb` и WORM (S2) со сверкой по периодам. Отключение систем RB, P2P-интеграций RB и FU Data Lake после 30 дней без обращений. Отзыв доступов, удаление временных компонентов | Критерии завершения из [migration-target-state.md](migration-target-state.md) выполнены, владельцы подписали приёмку |
